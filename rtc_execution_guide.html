RTC 执行过程详解

从控制线程、后台推理线程、动作队列到 flow-matching 去噪引导，完整解释 LeRobot 如何让高延迟 VLA 策略在机器人持续运动时生成下一段动作，并平滑替换旧动作轨迹。

异步执行 机器人执行旧动作时，后台并行生成下一段 action chunk。
重叠引导 新 chunk 的前缀在去噪过程中向旧 chunk 的剩余轨迹靠拢。
延迟对齐 新结果到达后丢弃已经过时的前缀，再替换执行队列。

1. RTC 解决什么问题

Pi0、Pi0.5、SmolVLA 等策略不是每次只预测一个动作，而是一次生成一段未来动作， 例如 50 个控制步。问题在于大模型推理可能耗时数百毫秒，而机器人控制周期可能只有 20～50 毫秒。

只做同步推理

控制线程等待模型返回，机器人会暂停或降低控制频率。

只做异步推理

虽然不会暂停，但新旧 chunk 可能对同一未来时刻给出完全不同的动作。

RTC

异步生成新 chunk，并在生成阶段约束其前缀，使新旧轨迹连续衔接。

一句话理解： RTC = 异步 action chunk 推理 + 推理延迟估计 + 新旧 chunk 重叠区引导 + 延迟后队列替换。

RTC 是推理时方法，不要求重新训练策略。它最适合使用 flow matching 生成动作的 chunk-based 策略。

2. 运行时架构

LeRobot 将 RTC 分成两个持续并行的执行路径：

主控制线程负责

  • 按照目标 FPS 读取机器人 observation。
  • 把最新 observation 发布给推理线程。
  • 从 ActionQueue 取一个动作。
  • 通过插值器和机器人 action processor 发送动作。

RTC 后台线程负责

  • 监控队列中剩余动作数量。
  • 估计推理对应多少个控制步。
  • 读取旧 chunk 的未执行部分。
  • 生成、后处理并合并新的 action chunk。
关键点： 两个线程共享的核心对象是线程安全的 ActionQueue。队列通过 Lock 保护，避免取动作与替换 chunk 同时修改状态。

3. 完整执行流程

创建引擎factory dispatch
→
启动线程start
→
恢复推理resume
→
控制循环obs / action

步骤 1：根据 CLI 配置创建 RTC 引擎

当 --inference.type=rtc 被选中时，factory 创建 RTCInferenceEngine，并把 policy、preprocessor、postprocessor、 机器人 wrapper、FPS、设备和 RTC 配置注入其中。

步骤 2：启动后台线程

start() 创建空的 ActionQueue、初始化 observation holder， 然后启动名为 RTCInference 的 daemon thread。线程启动后默认等待， 直到 rollout strategy 调用 resume()。

步骤 3：主控制循环发布 observation

每个控制循环都会读取原始 observation。经过 robot observation processor 后， notify_observation() 把它写入共享 holder。holder 只保留最新观测， 不会积压历史 observation。

为什么只保留最新 observation？ RTC 的目标是让下一段动作尽可能响应机器人当前状态。处理已经过时的 observation 只会增加额外延迟。

步骤 4：主线程持续消费动作

当插值器需要新目标动作时，主线程调用 engine.get_action()。 RTC 引擎不会在这里运行模型，只会从共享队列弹出一个已经准备好的动作，因此控制线程不会被大模型推理阻塞。

步骤 5：后台线程在队列低水位时启动推理

当 queue.qsize() <= queue_threshold 时，后台线程：

  1. 记录推理开始前的队列消费索引 idx_before。
  2. 读取旧 chunk 尚未消费的原始动作 prev_actions。
  3. 用历史最大推理耗时估算本轮 inference_delay。
  4. 构造模型输入并执行 preprocessor。
  5. 调用 policy.predict_action_chunk(...)。
control_period = 1 / fps
inference_delay = ceil(max_recorded_latency / control_period)

使用向上取整是保守策略：只要推理耗时跨过下一个控制周期，就按额外一个动作步计算， 避免低估已经过去的时间。

步骤 6：模型在每个去噪步骤应用 RTC guidance

Policy 先进行普通 flow-matching 速度预测；如果存在旧 chunk 的 leftover， RTCProcessor 会计算重叠区误差和梯度修正，让新 chunk 的前缀向旧轨迹靠拢。 第一轮推理没有旧 chunk，因此自动退化为标准 action chunk 生成。

步骤 7：后处理并测量真实延迟

新 chunk 生成后，一份未经 postprocessor 的动作保留在 original_queue， 另一份经过 postprocessor 后放入机器人执行队列。随后按本轮真实耗时重新计算 new_delay。

步骤 8：丢弃过时前缀并替换队列

推理期间机器人一直在执行旧 chunk，因此新 chunk 的前若干动作对应的时刻已经过去。 ActionQueue.merge() 会丢弃新 chunk 的前 new_delay 步， 再用剩余动作整体替换旧队列。 

original_queue = original_actions[new_delay:]
queue          = processed_actions[new_delay:]
last_index     = 0

步骤 9：循环继续

主线程随后开始消费新队列。等剩余动作再次低于 threshold，后台线程再次读取 leftover， 生成下一段 action chunk，形成持续滚动的实时控制。

5. Flow-matching 去噪中的 RTC 引导

仅仅异步替换队列还不够。新 chunk 独立生成时，它的开头可能与旧 chunk 当前正在执行的方向不一致。RTC 把新 chunk 的重叠前缀看作一个类似 inpainting 的约束问题。

5.1 前缀权重区域

权重 = 1
0 ～ inference_delay
权重逐渐衰减
inference_delay ～ execution_horizon
权重 = 0
execution_horizon 之后

已经被推理延迟覆盖的区域使用最强约束；随后逐步减弱，使模型最终可以根据最新 observation 自由调整远期动作。这样在“连续性”和“反应性”之间形成软过渡。

5.2 每个去噪步的代码逻辑

对于当前噪声状态 x_t：

  1. 原始 policy denoiser 给出基础速度 v_t。
  2. 由当前状态和速度估计最终干净动作 x1_t。
  3. 计算它与旧 chunk leftover 的加权误差。
  4. 通过 autograd 求误差对 x_t 的修正方向。
  5. 将修正项按动态 guidance weight 加到基础速度上。
x1_t = x_t - time · v_t
error = (previous_leftover - x1_t) · prefix_weights
correction = ∂x1_t / ∂x_t applied to error
guided_v_t = v_t - guidance_weight · correction

最后，policy 仍按原本的 flow-matching 更新规则执行：

dt = -1 / num_steps
x_t ← x_t + dt · guided_v_t

5.3 Guidance weight

LeRobot 根据当前去噪时间动态计算 guidance weight，并用 max_guidance_weight 截断。越接近去噪终点，修正能够更直接地控制最终动作； 上限用于避免修正过强导致数值或轨迹不稳定。

5.4 四种 prefix schedule

Schedule 重叠区行为 特点
EXP 从强约束非线性衰减到 0 通常适合作为起点，衔接柔和。
LINEAR 从 1 线性下降到 0 行为直观，当前配置类默认值。
ONES 整个 execution horizon 都为 1 最强调连续性，但可能降低对新状态的反应。
ZEROS delay 前为 1，之后立即变成 0 硬切换，过渡区没有平滑衰减。
第一次推理： prev_chunk_left_over is None，RTCProcessor 直接返回基础 v_t，不会施加任何引导。只有从第二个 chunk 开始才存在新旧轨迹衔接。

6. ActionQueue 如何保存和合并动作

original_queue

保存 policy 原始输出，主要用于下一轮 RTC guidance。它仍位于模型动作空间中， 因而能直接与下一次生成过程对齐。

queue

保存经过 policy postprocessor 的动作，是主控制线程实际取出并交给机器人执行的版本。

6.1 取动作

get() 返回 queue[last_index] 的 clone，然后 last_index += 1。clone 防止队列内部 tensor 被外部代码意外修改。

6.2 获取 leftover

prev_chunk_left_over = original_queue[last_index:]
processed_left_over  = queue[last_index:]

last_index 之前的动作已经执行，不应再约束下一段轨迹；只有尚未执行的尾部才是 RTC 的对齐目标。

6.3 RTC 模式的 merge

当 RTCConfig.enabled=True 时，merge 采用“替换”而不是“追加”： 

clamped_delay = clamp(real_delay, 0, len(new_chunk))
original_queue = original_actions[clamped_delay:].clone()
queue          = processed_actions[clamped_delay:].clone()
last_index     = 0

替换允许新策略根据最新 observation 修正未来计划；如果只是把新 chunk 追加到旧 chunk 后面，机器人会长期执行基于旧 observation 生成的动作，响应性很差。

6.4 为什么同时记录推理前索引

后台推理开始时记录 action_index_before_inference。推理结束后， 当前 last_index 与旧索引之差表示推理期间实际消费的动作数量。 代码会将它与按耗时计算的 real_delay 比较并记录 debug 信息。

7.3 相对动作的重新锚定

如果 preprocessor 中启用了 RelativeActionsProcessorStep，旧 chunk 的动作是相对于旧状态表达的，而新一轮模型输入基于当前状态。 直接把旧相对动作作为 guidance 前缀，会产生坐标系错位。

RTC 引擎因此执行以下转换：

  1. 读取队列中 postprocessed leftover，获得旧动作的绝对表示。
  2. 读取 RelativeActionsProcessorStep 缓存的当前原始 state。
  3. 以当前 state 为锚点，重新生成相对动作前缀。
  4. 必要时再次归一化到 policy 的输入动作空间。
这一步不能省略： 对 relative-action policy 而言，“相同的相对数值”不一定表示“相同的绝对目标”。 重新锚定确保 RTC 比较的是同一物理轨迹。

7.4 固定前缀长度

leftover 在送入 policy 前会被截断或补零到 execution_horizon。 固定形状有利于稳定的 torch.compile 图，避免每次剩余动作数量变化导致重新编译。

8. 关键参数与调优

参数 作用 增大后的影响 建议
execution_horizon 新旧 chunk 进行前缀约束的最大长度。 更平滑，但新 chunk 更难快速改变策略。 可从 8～12 开始。
max_guidance_weight 限制 RTC 修正强度。 旧轨迹约束更强，过大可能僵硬或数值不稳。 10-step flow matching 可从 10.0 开始。
prefix_attention_schedule 定义重叠区内约束如何衰减。 取决于具体 schedule。 希望柔和过渡时优先尝试 EXP。
queue_threshold 队列剩余多少动作时触发下一轮推理。 更早开始推理、缓冲更充足，但 observation 可能更旧。 必须结合 chunk size 和推理延迟调节。
fps 用于计算控制周期和离散 inference delay。 相同推理秒数会对应更多 delay steps。 必须与实际控制频率一致。

调参判断

chunk 交界仍然抖动

  • 提高 execution_horizon。
  • 提高 max_guidance_weight。
  • 检查 FPS 和真实控制周期是否一致。
  • 确认 relative actions 已正确重新锚定。

动作过于保守、反应迟缓

  • 减小 execution_horizon。
  • 减小 max_guidance_weight。
  • 使用衰减更快的 schedule。
  • 避免把 queue_threshold 设得过大。
平衡关系： RTC 的核心取舍是 continuity 与 reactivity。重叠约束越长、越强，chunk 边界越平滑；但策略对突然出现的新障碍或状态变化也会响应得更慢。

9. torch.compile Warmup、暂停与异常处理

9.1 Compile warmup

启用 torch.compile 时，最初若干次推理用于编译和 warmup， 耗时通常不能代表稳定运行延迟。RTC 会：

  1. 等待配置数量的 warmup inference 完成。
  2. 在 warmup 期间重置 latency tracker，避免编译耗时污染延迟估计。
  3. warmup 完成后清空 policy、processor、action queue 和 interpolator 的旧状态。
  4. 重新恢复后台推理，开始正式 rollout。

9.2 Pause / resume / reset

调用 效果
pause() 清除 active event，后台线程停止启动新推理，但线程本身仍存在。
resume() 设置 active event，允许后台线程继续检查 observation 和队列。
reset() 重置 policy、preprocessor、postprocessor，并清空 ActionQueue。
stop() 设置 shutdown event，并等待后台线程退出，join 超时为 3 秒。

9.3 推理失败

单次异常被视为临时错误，线程等待 0.5 秒后重试。连续失败达到 10 次时：

  • 设置 RTC failed 标记。
  • 解除可能正在等待 warmup 的主线程。
  • 设置全局 shutdown event，让 rollout strategy 退出控制循环。
队列耗尽： get_action() 会返回 None，不会伪造一个成功动作。 上层只有在插值器已有可用输出时才能继续发送动作。实际部署应确保 chunk、threshold 和推理性能能提供足够缓冲。

10. 与源码对应的简化伪代码

主控制线程

engine.start()
engine.resume()

while not shutdown:
    loop_start = now()

    obs_raw = robot.get_observation()
    obs_processed = robot_observation_processor(obs_raw)
    engine.notify_observation(obs_processed)

    if interpolator.needs_new_action():
        action = engine.get_action(obs_processed)
        if action is not None:
            interpolator.add(action)

    action = interpolator.get()
    if action is not None:
        action = robot_action_processor(action, obs_raw)
        robot.send_action(action)

    sleep_until_next_control_tick(loop_start, fps)

RTC 后台线程

latencies = LatencyTracker()
control_period = 1.0 / fps

while not shutdown:
    if not active:
        sleep()
        continue

    obs = latest_observation
    if obs is None or queue.qsize() > queue_threshold:
        sleep()
        continue

    start = now()
    index_before = queue.get_action_index()
    previous_leftover = queue.get_left_over()

    estimated_delay = ceil(latencies.max() / control_period)
    batch = preprocess(obs)
    previous_leftover = maybe_reanchor_relative_actions(previous_leftover)
    previous_leftover = pad_or_truncate(previous_leftover, execution_horizon)

    original_actions = policy.predict_action_chunk(
        batch,
        inference_delay=estimated_delay,
        prev_chunk_left_over=previous_leftover,
    )
    processed_actions = postprocess(original_actions)

    measured_latency = now() - start
    real_delay = ceil(measured_latency / control_period)
    latencies.add(measured_latency)

    queue.merge(
        original_actions,
        processed_actions,
        real_delay,
        index_before,
    )

单个 flow-matching 去噪步骤

base_velocity = policy_denoise_step(x_t)

if previous_leftover is None:
    velocity = base_velocity
else:
    weights = build_prefix_weights(
        inference_delay,
        execution_horizon,
        chunk_size,
    )
    predicted_clean_action = x_t - time * base_velocity
    error = (previous_leftover - predicted_clean_action) * weights
    correction = autograd(predicted_clean_action, x_t, error)
    velocity = base_velocity - guidance_weight * correction

x_t = x_t + dt * velocity

11. 如何启动 RTC rollout

lerobot-rollout \
  --strategy.type=base \
  --policy.path=${HF_USERNAME}/policy_repo_id \
  --inference.type=rtc \
  --inference.rtc.execution_horizon=10 \
  --inference.rtc.max_guidance_weight=10.0 \
  --inference.queue_threshold=30 \
  --robot.type=so100_follower \
  --robot.port=/dev/tty.usbmodem58FA0834591 \
  --task="Move the object to the target" \
  --duration=120 \
  --device=cuda

选择 RTC inference engine 后，policy 必须支持在 predict_action_chunk() 中接收 inference_delay 和 prev_chunk_left_over，并在内部的 flow-matching 循环中调用 RTCProcessor.denoise_step()。

当前典型支持策略： Pi0、Pi0.5 和 SmolVLA。是否可用最终取决于对应 policy 实现是否接入 RTCProcessor， 不能只通过 CLI 强行让任意 policy 获得 RTC 能力。

12. 常见问题

RTC 和普通异步推理有什么区别？
普通异步推理只解决“模型计算时机器人不要停下来”；RTC 进一步解决“新旧 chunk 在交界处不要跳变”。LeRobot 的 RTC engine 同时包含异步执行和 RTC guidance。
为什么 guidance 使用 original_queue，而执行使用 processed queue？
Guidance 发生在模型动作空间，应该与 policy 原始输出比较；机器人执行则需要经过反归一化、 action mapping 等 postprocess。混用两种空间会造成尺度和语义不一致。
为什么用历史最大延迟，而不是最后一次延迟？
最大延迟是保守估计，可降低偶发推理抖动导致 guidance 区间不足的风险。 LatencyTracker 默认维护最近 100 个样本，但其 max_latency 是自 reset 以来的最大值；warmup 后会 reset。
execution_horizon 必须大于 inference_delay 吗？
最好让 horizon 覆盖典型 delay 并留出柔和衰减区。实现中 start = min(inference_delay, execution_horizon)，因此 delay 超过 horizon 时不会越界，但整个 horizon 会成为强约束区，失去渐变过渡。
如果推理时间比整个 chunk 的执行时间还长会怎样？
merge 会把 delay clamp 到 chunk 长度，结果可能是空队列。此时 RTC 无法维持连续控制。 应减小模型延迟、降低控制 FPS、增大 chunk size，或部署更快硬件，而不能只靠调 guidance 参数解决。
RTC 会修改训练过程吗？
不会。RTCProcessor 只在推理的 action sampling / denoising 路径中工作； policy 的训练 loss 和训练数据不需要因此改变。
